# S3 / Storage Architecture

## Overview

GNOVIUM uses a content-addressable storage (CAS) system. Every file is identified by its SHA-256 hash, enabling automatic deduplication. Two storage backends implement the same interface:

- **LocalProvider** — local filesystem storage used in local mode
- **S3Provider** — AWS S3 storage used in cloud mode

The active provider is selected at startup via configuration. The factory inspects `GNOVIUM_MODE` and `S3_BUCKET`: if mode is `cloud` and a bucket is configured, S3Provider is returned; otherwise LocalProvider defaults to `<instance_path>/objects`.

## Object Key Layout

All keys live under layout version `v1/`. They are deterministic — the same inputs always produce the same key, enabling automatic deduplication.

### Object keys (`v1/objects/`)

```
v1/objects/{variant}/{prefix_2}/{prefix_2}/{full_sha256}{ext}
```

- `variant` — `original`, `derived/thumbnail`, `derived/preview`, `derived/optimized`, or `derived/pdf-pages`
- `prefix_2` — first 2 hex chars of the SHA-256 hash (256-way sharding)
- `prefix_2` — next 2 hex chars (creates a nested directory)
- `full_sha256` — the complete 64-character SHA-256 hex digest
- `ext` — file extension when present (`.webp` for variants)

Example: `v1/objects/original/ab/cd/abcdef0123456789...ff.jpg`

### Temp keys (`v1/temp/`)

```
v1/temp/pending/{prefix_2}/{prefix_2}/{uuid_hex}
```

Temporary staging keys used during presigned uploads before the file is finalized. The UUID hex provides uniqueness. Created for both single-part and multipart presigned uploads.

### Quarantine keys (`v1/quarantine/`)

```
v1/quarantine/{reason}/{content_hash}
```

Where `reason` is one of: `invalid` (bad extension or MIME type), `virus` (malware detected), `failed` (scan error).

### Avatar keys (`v1/avatars/`)

```
v1/avatars/{user_id}/{content_hash}.{ext}
```

User profile images uploaded via `POST /auth/avatar`. Content-addressed using SHA-256 of the file bytes — same as the main object storage. The user ID provides per-user isolation, and the hash ensures the filename is unpredictable and deduplicated. The extension is derived from the uploaded file's MIME type.

### Local mode layout

Local mode uses a flatter layout for backwards compatibility:

```
objects/original/{prefix}/{sha256}            — raw uploaded bytes
objects/thumbnail/{prefix}/{sha256}.webp      — ≤256px WebP variant
objects/preview/{prefix}/{sha256}.webp        — ≤1024px WebP variant
objects/optimized/{prefix}/{sha256}           — compressed variant
```

Variant cleanup: in local mode, the LocalFileRepository removes all variant files (thumbnail, preview, optimized) from disk whenever a file record is soft-deleted or hard-deleted, by walking the tier directories and deleting matching files. LocalProvider also provides `delete_all_variants` for direct variant cleanup. In cloud mode, variants are soft-deleted through the FileVariant repository.

## Bucket Configuration

When the bucket is first set up, the following are applied:

1. **Versioning** — enabled on the entire bucket via `put_bucket_versioning`
2. **Public Access Block** — all four public access settings blocked
3. **Object Lock** — enabled with GOVERNANCE mode default retention of 30 days
4. **Lifecycle Rules** — 5 rules applied via `put_bucket_lifecycle_configuration`

### Lifecycle Rules

| Rule ID | Prefix | Action | Details |
|---------|--------|--------|---------|
| `gnovium-temp-cleanup` | `v1/temp/` | Expiration + Abort MPU | Expire objects after 7 days; abort incomplete multipart uploads after 1 day |
| `gnovium-quarantine-retention` | `v1/quarantine/` | Expiration | Delete quarantined objects after 30 days |
| `gnovium-deleted-object-cleanup` | `v1/objects/` | Expired object delete marker | Clean up delete markers left by versioned deletes |
| `gnovium-glacier-transition` | `v1/` | Storage class transitions | STANDARD_IA after 90 days, GLACIER after 180 days, DEEP_ARCHIVE after 365 days |
| `gnovium-noncurrent-expiration` | `v1/` | Noncurrent version expiration | Expire noncurrent versions after 90 days |

Lifecycle rules are applied during bucket initialization (via the folder setup script) and are never automatically called at runtime. They must be reconfigured manually or through the setup process.

## Storage Providers

### Common Interface

Both providers implement the same abstract interface with these operations:

- **store** — write bytes at a key with a content type
- **retrieve** — read raw bytes from a key
- **delete** — remove an object by key
- **exists** — check if an object exists
- **size** — get the byte size of an object
- **presign_upload** — generate a presigned upload URL (S3) or return a stub (local)
- **presign_download** — generate a presigned download URL (S3) or return a filesystem path (local)
- **generate_object_key** — generate a deterministic object key from workspace, filename, and content hash
- **generate_variant_key** — generate a deterministic variant key from tier, content hash, and extension
- **has_variant** — check whether a variant exists for the given tier and content hash
- **store_variant** — store a processed variant and return its object key
- **retrieve_variant** — retrieve a variant's bytes by tier and content hash
- **delete_variant** — delete a single variant
- **delete_all_variants** — remove all variants (thumbnail, preview, optimized) for a content hash

All S3 operations are wrapped in a circuit breaker that trips after 5 failures with a 60-second recovery timeout. The circuit has three states: CLOSED (normal operation), OPEN (rejecting requests), and HALF_OPEN (probing after timeout). It is thread-safe and counts successes separately, resetting the failure count on any success.

### LocalProvider

Stores files directly on the local filesystem under a configurable root directory. Operations:

- Path traversal is prevented by resolving keys against the storage root and rejecting any path that escapes it
- All CRUD operations create parent directories as needed
- Empty parent directories are cleaned up after deletes
- Provides variant storage helpers (`store_variant`, `retrieve_variant`, `has_variant`, `delete_variant`, `delete_all_variants`)
- Provides an orphan cleanup walker that scans the `objects/` directory and removes files not referenced by any non-deleted database record
- Provides per-tier storage statistics (count and total bytes for original, thumbnail, preview, optimized)
- Presigned operations return stubs indicating presigned URLs are unsupported in local mode

### S3Provider

Wraps the AWS SDK to interact with S3. Operations:

- All object storage uses server-side encryption (AES-256)
- The S3 client is created lazily on first access with configurable region and credentials
- Presigned upload returns a PUT URL with a calculated expiration timestamp
- Presigned download supports optional `response_content_type` and `response_content_disposition` overrides
- Multipart upload support with `create_multipart_upload` and `complete_multipart_upload`
- Variant management: `generate_variant_key`, `has_variant`, `store_variant`, `retrieve_variant`, `delete_variant`, `delete_all_variants` — delegates to module-level derived key generation (`generate_derived_key`) for S3 key layout
- `generate_object_key` — delegates to module-level `generate_object_key` with the `original` variant
- Enables versioning, object lock, and configures lifecycle rules on the bucket
- Stores all data with `STANDARD` storage class by default; lifecycle rules transition to colder tiers

## File State Machine

Files in cloud mode follow a state machine:

```
PENDING ──► UPLOADED ──► VALIDATING ──► READY
               │              │              │
               │              │ (error)      ▼
               │              ▼           QUARANTINED
               │           PENDING            │
               │                        ┌─────┴──────┐
               │                    (approve)    (reject)
               │                        │            │
               │                        ▼            ▼
               │                     READY        DELETED
               │
               ↓ (cleanup_expired_pending)
             DELETED / hard-deleted
```

- **PENDING → DELETED/hard-deleted**: automatic cleanup via `cleanup_expired_pending()` — soft-deletes in cloud mode, hard-deletes (DB + disk) in local mode after 7 days
- **VALIDATING → PENDING**: error recovery — a failed validation rolls back the state to allow retry
- **QUARANTINED → DELETED**: automatic clean-up via `cleanup_expired_quarantine()` — soft-deletes after 30 days in cloud mode, hard-deletes locally
- **READY/QUARANTINED/UPLOADED → DELETED**: user-initiated via `delete_file_cloud()` (cloud) or `delete_file()` (local) — always soft-delete

- **PENDING** — File record created but bytes not yet uploaded (presigned flow)
- **UPLOADED** — Bytes confirmed in storage, waiting for validation
- **VALIDATING** — Validation (MIME, extension, virus scan) in progress
- **READY** — File passed validation and is available for download
- **QUARANTINED** — File flagged by validation (invalid, virus, or scan error)
- **DELETED** — Soft-deleted (either by user or automatic cleanup)

Local mode bypasses the state machine entirely: files go directly from upload to available, with inline processing during the upload call. The FileRepository is swapped for a LocalFileRepository that manages file deletion by removing files (and all their variants) from disk immediately on soft-delete or hard-delete.

## Upload Flow

### Local Mode

1. Client sends multipart form data to the upload endpoint
2. File is validated: extension against allowed list, MIME type, magic bytes signature check
3. File bytes are hashed with SHA-256
4. Storage quota is checked (aggregate SUM query, no row-level lock)
5. Deduplication check: if a non-deleted file with the same content hash exists in the same workspace, the existing record is returned immediately
6. A deterministic object key is generated from the content hash
7. Raw bytes are stored via the provider
8. Database record is created
9. For images ≤10MB: thumbnail (256×256 WebP at quality 80), preview (1024×1024 WebP at quality 85), and optimized (WebP at quality 80) variants are generated inline using PIL
10. For PDFs ≤50MB: text is extracted using PyMuPDF (first 20 pages)

### Cloud Mode

1. Client requests a presigned upload URL with file metadata
2. File name and MIME type are validated; quota is checked
3. If a content hash is provided and a matching file exists, the existing record is returned (early dedup)
4. A temporary object key is generated under `v1/temp/pending/`
5. A presigned PUT URL is returned along with a file ID in PENDING state
6. Client uploads bytes directly to S3 using the presigned URL
7. Client confirms the upload via the confirm endpoint, which:
   - Verifies the file is in PENDING state
   - Checks the object exists in S3
   - Computes the SHA-256 hash by streaming from S3
   - Re-checks deduplication (handles concurrent upload race with integrity error retry)
   - Re-keys the object from temp to its final content-addressed key under `v1/objects/original/`
   - Deletes the temp key
   - Transitions state to UPLOADED

If the S3 presigned upload fails (e.g., network error, CORS configuration), the frontend falls back to the direct upload endpoint (`POST /files/upload`), which streams the file through the Flask server to S3 via `provider.store()`. This ensures uploads work even without direct browser-to-S3 connectivity.

For large files, clients can use multipart upload: initiate via presign-multipart, upload parts to presigned URLs, then complete with ETag list. The completion endpoint calls `complete_multipart_upload` on S3 then delegates to the same finalization logic.

After upload confirmation, if inline processing is enabled, validation runs immediately:
- File extension and MIME type checks
- Optional ClamAV virus scan (with retry on timeout/error)
- On success: file transitions to READY and derived jobs are enqueued
- On failure: file is moved to quarantine storage and the uploader is notified

If inline processing is disabled, a validation job is enqueued for background processing.

## Download Flow

All download and variant endpoints (`/download`, `/thumbnail`, `/preview`, `/optimized`) return JSON instead of directly serving the file or doing a server-side redirect:

### Local Mode

The endpoint returns `{"presigned_url": ".../download?direct=1"}`. When the browser or fetch caller follows the URL with `?direct=1`, the backend resolves the object key to a local filesystem path and serves the file directly using `send_from_directory` with the original filename and MIME type. Path traversal is blocked by resolving both the directory and file path and verifying they stay within the storage root.

### Cloud Mode

The endpoint returns `{"presigned_url": "https://s3-bucket.s3.amazonaws.com/..."}` — a presigned GET URL generated by the S3 provider that expires after a configurable duration (default 1 hour). The frontend uses `window.open(res.data.presigned_url)` to navigate to the S3 URL directly.

### Variant Endpoints

The `/thumbnail`, `/preview`, and `/optimized` endpoints follow the same pattern:
- **Cloud**: returns `{"presigned_url": "..."}` pointing to the S3 variant object
- **Local**: returns `{"presigned_url": "...?direct=1"}` which serves the local variant file

### Frontend Usage

The frontend methods `getDownloadUrl()`, `getThumbnailUrl()`, `getPreviewUrl()`, and `getOptimizedUrl()` call `apiClient.get()` and expect `{ data: { presigned_url: string } }` in the response. The presigned URL is then used in `window.open()` or as an `<img>`/`<iframe>` `src`.

## Variants

Three image variant types are produced:

| Variant | Max Dimension | Format | Quality | Purpose |
|---------|--------------|--------|---------|---------|
| Thumbnail | 256×256 | WebP | 80 | Gallery/list views |
| Preview | 1024×1024 | WebP | 85 | Lightbox/inline display |
| Optimized | Original size | WebP | 80 | Bandwidth-optimized download |

In **local mode**, variants are generated inline during upload using PIL. They are stored as files on disk under `objects/{tier}/{prefix}/{hash}.webp`.

In **cloud mode**, variants are generated asynchronously through the job queue. The pipeline:
1. Retrieves original bytes from S3
2. Processes the image (resize + encode as WebP)
3. Stores the result at a derived key under `v1/objects/derived/{variant_type}/`
4. Creates a FileVariant database record with algorithm metadata

Variants are determined by the original content hash — all variants of a file share the same hash, so each file can have at most one thumbnail, preview, and optimized variant per content hash. The variant endpoints serve the file directly (local) or redirect to a presigned URL (cloud).

For **PDF files** in cloud mode, up to 10 pages are rendered as WebP images at 150 DPI and stored as `derived/pdf-pages` variants.

## Quarantine

Files that fail validation are quarantined:

1. The original bytes are copied to `v1/quarantine/{reason}/{hash}`
2. The database record is updated with the quarantine key and QUARANTINED state
3. The original object is deleted from its original location
4. A system notification is sent to the uploader

Quarantine reasons:
- `invalid` — file extension not in allowed list, or MIME type not in allowed set
- `virus` — ClamAV scan returned INFECTED
- `failed` — scan returned a non-recoverable error

Resolution (cloud-only, available to authorized users):
- **Approve**: state transitions from QUARANTINED to READY
- **Reject**: state transitions from QUARANTINED to DELETED (soft-delete)

Cleaning: expired quarantine records (configurable expiry, default 30 days) are soft-deleted in cloud mode; in local mode they are physically deleted from disk.

## Virus Scanning

Optional ClamAV integration enabled via configuration. When active:

1. File bytes are written to a temporary file
2. `clamscan --no-summary` is run with a 120-second timeout
3. If `OK` in stdout: clean; otherwise: infected
4. If clamscan is not found or times out: the scan is considered unavailable and the file proceeds (or a retry is attempted in the pipeline)
5. In the pipeline, a scan failure triggers a single retry before quarantining

## Processing Pipeline

### Local Mode

Processing is inline and synchronous during the upload call:
- Image: PIL generates thumbnail, preview, and optimized variants immediately
- PDF: PyMuPDF extracts text from the first 20 pages
- Text/JSON: metadata and extracted text are set directly

### Cloud Mode

Processing is asynchronous via a job queue:

1. After upload confirmation and validation, derived jobs are enqueued:
   - `image_thumbnail`, `image_preview`, `image_optimized` — for images ≤10MB
   - `pdf_pages` — for PDF files
   - `content_extract` — for PDF (≤50MB), text, JSON, and XML files
2. A job runner polls pending jobs using `SELECT ... FOR UPDATE SKIP LOCKED`
3. Each job is dispatched to the pipeline by type
4. On success: the job is marked completed; on failure: retried up to 3 times
5. If all retries are exhausted, the job is marked failed

The job runner supports concurrent workers through row-level locking.

## Deduplication

Deduplication is content-addressed using SHA-256 hashes:

- **At upload time**: before storing, the service checks for an existing non-deleted file with the same content hash in the same workspace
- **At finalization time**: for presigned uploads, the SHA-256 is computed from the stored bytes and checked again (protects against hash mismatch claims)
- **Concurrency safety**: a race condition between the dedup check and commit is handled with an integrity error retry — if two uploads finish simultaneously, one will get an integrity error and re-check, finding the other's record and deduplicating
- **Scope**: deduplication is per-workspace. The same content hash in different workspaces produces separate file records
- **Re-keying**: when a pending file's actual hash differs from the temporary hash, the object is moved from its temp key to its final content-addressed key

## Cleanup

| Type | What it does | Scope | Configuration |
|------|-------------|-------|---------------|
| Expired Pending | Removes stale PENDING file records (presigned uploads never confirmed) | Local: provider.delete + session hard_delete; Cloud: soft-delete only | `TEMP_EXPIRATION_DAYS` (default 7) |
| Expired Quarantine | Removes quarantined files past retention | Local: provider.delete + delete_all_variants + session hard_delete; Cloud: soft-delete only (S3 lifecycle handles physical deletion) | `QUARANTINE_EXPIRATION_DAYS` (default 30) |
| Deleted Files | Removes soft-deleted files past retention | Cloud: provider.delete + session hard_delete (S3 lifecycle handles variants via noncurrent expiration); Local: provider.delete_all_variants + provider.delete + session hard_delete | `DELETED_RETENTION_DAYS` (default 30) |
| Orphan Files (Service) | Removes file records with no entity links | Soft-deletes records + sets state=DELETED; LocalFileRepository also removes files from disk | — |
| Orphan Files (Provider) | Walks objects/ directory and removes files not in any active DB record | LocalProvider only; deletes orphan disk files | — |
| S3 Lifecycle | Physical deletion of temp, quarantine, noncurrent versions, and delete markers | S3 lifecycle rules handle actual S3 object cleanup | Applied during bucket setup |
